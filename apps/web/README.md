# честный поиск товаров — клиентская версия (you.market), версия 3.1.0

Одностраничник без серверов и прокси: **всё выполняется в браузере
пользователя и от его лица** — его вкладки, его IP, его куки. Поисковик видит
обычного человека, а не бота: мы не конкуренты поисковым системам, мы их
активные пользователи, просто немного более продвинутые.

**Сайт:** https://judgedikirsanov-dotcom.github.io/you.market
(статический, публикуется из этого репозитория через GitHub Pages).

**Выпуски:** https://github.com/judgedikirsanov-dotcom/you.market/releases —
архив расширения, скрипт, суммы SHA-256, заметки. Журнал изменений — в
`CHANGELOG.md` в корне репозитория.

## Что изменилось в 3.1.0

- **«Шаттл» (этап 2 дорожной карты).** Вместо отдельного окна на каждый
  источник — одна вкладка с очередью источников: закладка (или скрипт-мост)
  передаёт выдачу через страницу-релей, релей ведёт вкладку к следующему
  источнику, после последнего вкладка закрывается. Подробности — ниже.
- **Выбор канала сбора (шаг 8).** Пользователь ничего не настраивает: страница
  берёт лучший доступный канал — расширение-мост, затем «Шаттл», затем окна —
  и показывает выбор в строке статуса. Запасной селектор — в панели.
- **Релизы (шаг 5).** Выпуск собирается по метке `vX.Y.Z`: архив расширения,
  скрипт, суммы SHA-256 и манифест `latest.json`, с аттестатом сборки. На
  странице есть ссылки на файлы последнего выпуска.
- **Закладка и скрипт-мост** всегда отчитываются через страницу-релей (так
  «Шаттл» узнаёт вернувшуюся вкладку). Скрипт объявляет себя странице, в нём
  прописаны адреса обновления.
- **Устаревшая вкладка.** Раз в час страница сверяет свою версию с
  `version.json` сайта и предлагает обновиться.

## Что изменилось в 3.0.0

- **Дизайн.** На странице остались только главное: строка поиска и карточки
  товаров. Всё служебное (закладка, план запроса, стадии, контрольные запросы,
  журнал) убрано в свёрнутую панель «технические детали» внизу. Цвета — серые
  с мягкими градиентами, без ярких акцентов.
- **Планировщик запросов** (`planner.js`, «Честный поиск 2.0», этап 1). Запрос
  разбирается на намерение и сущности, для каждого источника строится свой
  текст запроса, а карточки получают одну взвешенную оценку релевантности
  вместо четырёх прогонов фильтра по словам. Подробности — ниже.
- **Диагностика этапа 0.** В панели — 30 контрольных запросов с готовым планом,
  ссылки для проверки параметров диалектов поисковиков (P6, P8, P11) с
  отметками «сработало / не сработало» и кнопка «скачать отчёт этапа 0»
  (JSON: план, карточки трёх вердиктов с причинами, метрики).
- **Единая версия.** Номер хранится один раз — в `version.json` — и
  проставляется во все части продукта сборщиком; сверка версий идёт в CI.

## Как работает поиск

Пользователь вводит запрос и жмёт «искать». Дальше:

1. **планировщик строит план**: намерение (купить / купить б/у / выбрать /
   изучить), сущности (бренд, модель, категория, уточнения, атрибуты, бюджет),
   тексты запросов для Яндекса, Google и площадок и список источников —
   3–4 по намерению: «купить» → Яндекс, Ozon, Google; «б/у» → Авито, Яндекс,
   Google; «выбрать» → Google, Яндекс, DuckDuckGo; «изучить» → Google,
   DuckDuckGo;
2. **страница выбирает канал сбора** и открывает источники. По умолчанию это
   **одна вкладка «Шаттл»** с очередью источников (у каждого — свой текст
   запроса). С расширением-мостом поисковики уходят «под капотом», без вкладок.
   Запасной режим — прежний каскад окон «друг под другом», где последним
   открывается окно-анимация (`#fsWorker`): перекрывает стопку, показывает
   живой прогресс и закрывается на «готово»;
3. в каждой вкладке выдача разбирается **прямо на месте**:
   - **кнопка-закладка (букмарклет)** — один клик по закладке «📨 в фильтр
     товаров»; код полностью инлайновый (CSP поисковиков javascript:-URL
     закладок не запрещает), работает в Firefox, Chrome, Safari, Edge;
   - **пользовательский скрипт** (`filter-search.user.js` для
     Violentmonkey/Tampermonkey) — то же самое **без единого клика**: вкладка
     отчитывается сама;
   - **расширение-мост** (`apps/ext/`) — то же самое, без менеджера скриптов;
   - парсеры вынимают результаты **и ИИ-ответы поисковиков** (Google AI
     Overview, Яндекс Нейро, Bing Copilot, Brave AI);
4. данные попадают на страницу агрегатора через **страницу-релей**: закладка
   или скрипт навигируют вкладку на наш сайт с данными в адресе
   (`#fsRelay=<base64url>`), релей передаёт payload агрегатору через
   **BroadcastChannel** и решает, что делать со вкладкой дальше — закрыть или
   вести к следующему источнику;
5. **выдачи → итог**: карточки с источниками и ценами, перекрёстные
   подтверждения, медиана рынка; поздние вкладки вольются и пересчитают итог.
   ИИ-ответы показываются в панели отдельной карточкой — это справка
   поисковика, в медиану не входит.

## «Шаттл»: одна вкладка вместо окон (этап 2)

Задача — пройти 3–4 источника одним кликом на каждый и не оставлять после
себя стопку окон. Устройство (`shuttle.js`, `app.js`):

1. **Очередь.** По нажатию «искать» страница собирает очередь источников
   (порядок — от планировщика), каждому адресу добавляет маркер `&fsx=1&fsh=1`
   и записывает очередь в `sessionStorage` — хранилище собственной вкладки.
2. **Вкладка.** Сразу после записи страница открывает первую выдачу
   (`window.open`). Новая вкладка получает копию `sessionStorage` открывшей
   её вкладки — так очередь оказывается внутри самой вкладки «Шаттла» и
   переживает любые переходы по чужим сайтам. Свою копию страница стирает
   через две секунды, чтобы позже открытые вкладки её не наследовали.
3. **Отчёт.** На выдаче пользователь жмёт закладку (или срабатывает
   скрипт-мост). Вкладка уходит на страницу-релей с payload в адресе.
4. **Транзит.** Релей передаёт payload агрегатору по `BroadcastChannel`,
   читает очередь из хранилища вкладки, отмечает источник пройденным и через
   0,9 с ведёт ту же вкладку на следующий источник. Когда пройдены все —
   сообщает агрегатору `{fsShuttleDone}`, показывает «✓ готово» и закрывается
   (если браузер не разрешает закрыть — пишет «Ctrl+W»).

Релей узнаёт вкладку «Шаттла» не по адресу, а по наличию очереди в
хранилище: SPA-сайты (AliExpress) переписывают адрес и могут потерять
параметр. Маркер `fsh=1` в адресе остаётся как сигнал для двух частных
случаев — сразу скрыть страницу под экраном релея и сообщить, если маркер
есть, а очереди в хранилище нет.

Что делает страница, если что-то пошло не так:

| Ситуация | Поведение |
|---|---|
| браузер заблокировал всплывающую вкладку | в строке статуса появляется ссылка «открой её ссылкой» — нажатие открывает «Шаттл» вручную, очередь работает так же |
| вкладка вернулась с маркером, но без очереди (например, сайт источника открыл выдачу в новой вкладке) | сообщение `{fsShuttleLost}`: страница пишет ««Шаттл» потерял очередь» и подсказывает открыть остальные источники кнопками в «технических деталях» |
| отчёт пришёл после того, как итог собран | итог пересчитывается, строка статуса объясняет, что «Шаттл» ещё идёт |
| нет `sessionStorage` (жёсткие настройки приватности) или `window.open` | канал «Шаттл» недоступен — страница берёт окна |
| пользователь сбросил поиск | очередь сбрасывается, поздние отчёты старой очереди игнорируются (у каждой — свой `sid`) |

Закладка и скрипт-мост **всегда** идут через релей, без быстрого пути
`window.opener.postMessage`: по быстрому пути вкладка закрывалась бы после
первого отчёта и очередь обрывалась. Для обычных вкладок это ничего не меняет —
релей и раньше был запасным путём для сайтов с COOP.

Проверено в headless Chromium 143 (проба `sessionStorage` → `window.open` и
ссылкой `rel=opener`, закрытие после переходов, с `COOP: same-origin-allow-popups`
и без, с `history.pushState`). Firefox и Safari не проверялись.

## Выбор канала сбора (шаг 8)

Пользователь канал не настраивает. Перед поиском страница проверяет, что
доступно, и берёт первое подходящее (`channels.js`):

| Канал | Когда выбирается | Что видит пользователь |
|---|---|---|
| локальный помощник | помощник включён и ответил на `127.0.0.1` — **выключен до этапа 3** | ничего: кликов нет |
| расширение-мост | расширение объявилось на странице | кликов нет, вкладки идут под капотом |
| «Шаттл» | есть `sessionStorage` и `window.open` | одна вкладка, закладка на каждой выдаче |
| окна источников | всё остальное | прежний каскад окон |

Выбранный канал пишется в строку статуса и в журнал («канал сбора: «Шаттл» —
…»). В панели есть запасной селектор — «авто», ««Шаттл»», «окна»; выбор
хранится в `localStorage` этого браузера и действует с ближайшего поиска.
Если выбран «Шаттл», а он недоступен, — страница честно переходит на окна.

Помощник выключен намеренно: иначе браузер уже сейчас спрашивал бы
разрешение на обращение к локальной сети. Подсказка для этого разрешения
заготовлена (`channels.js`, `LOCAL_NET_HINT`) и включится на этапе 3.

## Что видит пользователь

- **строка поиска** — поле и кнопка «→». Пока пользователь в первый раз на
  странице и ещё не передал ни одной выдачи, под строкой одна небольшая
  кнопка «как передать выдачу — 1 минута»: она раскрывает панель с закладкой
  и инструкцией. После первой выдачи кнопка не показывается.
- **карточки товаров.** Один товар — одна карточка: слева название, справа
  источники с ценами. Впереди основные, похожие — свёрнуты в блок
  «похожие на запрос». Скрытые предложения не пропадают молча: их список с
  причинами — в панели и в отчёте.
- **строка статуса** — одна строка над карточками: сколько выдач пришло, что
  делать дальше. В режиме «Шаттла» — сколько источников осталось. Если
  основных предложений с ценой меньше трёх, в ней появляется кнопка смягчить
  запрос (шаг лестницы ослабления).

## Оценка карточек (planner.js)

Каждое предложение получает баллы и вердикт: **основная** (доля баллов ≥ 60 %
и не менее 3 баллов), **похожая** (≥ 35 %), **скрыта** (с причиной).

| Сигнал | Вес |
|---|---|
| бренд из запроса есть в названии | +3 (нет — карточка скрывается) |
| модель из запроса есть в названии | +3 (другая модель того же бренда скрывается) |
| категория есть в названии | +1 |
| каждое уточнение категории | +1 |
| атрибуты (размер, объём) | +2 за каждый, не более +4 |
| площадка или карточка товара | +2 — только при намерении «купить» |
| цена в бюджете | +1 — только если в запросе задан бюджет |
| информационный шум (обзор, отзыв, видео, форум) | −4 за признак, не менее −6 — только при «купить» |
| нет цены | −1 — при «купить» и не на площадке |
| аксессуар или запчасть | скрывается независимо от баллов (кроме запросов про сам аксессуар) |

Пример: запрос «sava a7l carbon» → намерение «купить», бренд SAVA, модель
a7l carbon; максимум 8 баллов. Карточка Ozon «Велосипед SAVA A7L Carbon 700C»
с ценой — 8/8, основная. Страница на сайте бренда без цены — 5/8, основная.
«SAVA A7L: обзор велосипеда» — скрыта: «другая модель бренда (нет „a7l
carbon“); к тому же это обзор или видео, а не предложение». «Педали для
велосипеда SAVA» — скрыта: «аксессуар или запчасть, а не сам товар».
«Carbon road bikes under $1000» — скрыта: «нет бренда запроса („sava“)».

Если основных предложений с ценой меньше трёх, планировщик предлагает лестницу
ослабления — по одному шагу: убрать минус-слова → убрать маркер покупки →
убрать кавычки → убрать атрибуты → без категории и модификаторов. С
расширением-мостом шаг применяется сам, в остальных режимах — кнопкой.

**Склейка.** Для запроса «бренд + модель» все магазины и модификации одной
модели попадают в одну карточку (у каждой ссылки-источника всплывает своё
название). Иначе ключ — значимые слова названия минус слова запроса: «детский
велосипед Stels Jet 14» из Ozon и со ссылки из выдачи — одна карточка, а
Stels, Forward и Merida — разные.

## Тесты и сборка

Нужен Node.js 24. Из корня репозитория:

```
node apps/web/tests/web_tests.js        # ядро: парсеры, фильтр, сравнение выдач
node apps/web/tests/planner_tests.js    # планировщик: план, жёсткие правила, веса, 30 контрольных запросов
node apps/web/tests/shuttle_tests.js    # «Шаттл»: очередь, обход, хранилище, выбор канала
node tools/test_bridge_lib.js           # мост: парсеры, ИИ-экстракция, payload
node tools/test_release_dist.js         # выпуск: архив, суммы, манифест, воспроизводимость, заметки
node tools/build_bookmarklet.js         # собрать закладку и проставить версию
node tools/build_bookmarklet.js --check # проверить, что сборка совпадает с репозиторием
node tools/check_versions.js            # сверить версии во всех частях продукта
```

Сценарий `checks` на каждую отправку запускает пять наборов тестов, сверку
сборки и версий, сборку папки выпуска и пробу заметок. Сценарий
`publish-web` перед публикацией сайта повторяет тесты и обе сверки.

## Единая версия

Номер хранится один раз — в `version.json` (`version` и `format`, номер
формата данных). Сборщик `node tools/build_bookmarklet.js` проставляет его в
пять мест: параметр `?v=` у библиотек страницы, метка `you-market-version`,
поля `@version` и `@require` пользовательского скрипта, поле `version` обоих
манифестов расширения. Для страницы адрес с новым номером — единственный
способ обновить библиотеку у посетителя.

`node tools/check_versions.js` падает, если где-то остался чужой номер или
файл скрипта, подключённого страницей, отсутствует; с ключом `--tag vX.Y.Z`
он сверяет метку релиза с `version.json`. Ту же проверку вызывает сборщик
выпуска — файл со старым номером в релиз не попадает.

## Релизы (шаг 5)

Выпуск собирает сценарий `release` по метке `vX.Y.Z` (файл
`.github/workflows/release.yml`). Состав папки выпуска — `tools/make_release_dist.js`:

| Файл | Что это | Как ставится |
|---|---|---|
| `filter-search-ext.zip` | расширение-мост: файлы `apps/ext/` в корне архива | распаковать → `chrome://extensions` → режим разработчика → «Загрузить распакованное расширение» |
| `filter-search.user.js` | скрипт-мост | Violentmonkey / Tampermonkey → открыть файл → «установить» |
| `SHA256SUMS.txt` | суммы SHA-256 в формате coreutils | `sha256sum -c SHA256SUMS.txt` |
| `latest.json` | манифест: версия, формат данных, минимальная версия страницы, суммы и размеры файлов | читают страница и помощник |

Архив собирается без сжатия и с фиксированной датой записей, поэтому
повторная сборка даёт байт в байт тот же файл: суммы из релиза можно
проверить, пересобрав выпуск из исходников. К файлам прикладывается аттестат
сборки (`actions/attest`) — проверить: `gh attestation verify filter-search-ext.zip --repo judgedikirsanov-dotcom/you.market`.

Постоянные ссылки (всегда последний выпуск):

- файлы: `https://github.com/judgedikirsanov-dotcom/you.market/releases/latest/download/<имя-файла>`
- страница выпуска с заметками: `https://github.com/judgedikirsanov-dotcom/you.market/releases/latest`

Заметки о выпуске собирает `tools/release_notes.js`: раздел текущей версии из
`CHANGELOG.md`, инструкции по установке, суммы и таблица файлов. Если в
`CHANGELOG.md` нет раздела для выпускаемой версии, сценарий останавливается.

### Как выпустить версию

1. Описать изменения: новый раздел `## vX.Y.Z — …` наверху `CHANGELOG.md`.
   Его заголовок станет заголовком релиза.
2. Поднять номер в `version.json`.
3. `node tools/build_bookmarklet.js` — проставит номер во все части продукта
   и соберёт закладку.
4. Прогнать проверки из раздела «Тесты и сборка»; по желанию —
   `node tools/make_release_dist.js` и взглянуть на `dist/`.
5. Отправить в `main`: `bash push.sh "что изменилось"`. Дождаться зелёных
   сценариев `checks` и `publish-web`.
6. Поставить метку на вершину `main` и отправить её:
   `git tag vX.Y.Z && git push origin vX.Y.Z`.

Дальше сценарий `release` сам повторяет проверки, сверяет метку с
`version.json`, проверяет, что метка стоит на вершине `main`, собирает папку
выпуска, подтверждает её воспроизводимость, подписывает аттестатом и создаёт
релиз с файлами и заметками. Релиз появляется только после аттестата: если
аттестат не удался, публикация не начинается.

Повторить выпуск той же метки (например, после правки сценария) — вкладка
Actions → release → Run workflow → имя метки: исполняется сценарий из `main`,
файлы заменяются, заметки обновляются. Для срочной правки старой версии
адрес файла указывают с явным номером: `releases/download/vX.Y.Z/<имя-файла>`.

## Почему без прокси и серверов

Публичные CORS-прокси работают с IP дата-центров — поисковики отдают им
капчи и мусор, то есть «спамботную» выдачу. Наш инструмент должен видеть ровно
то, что видит человек, поэтому источник выдачи — только вкладка пользователя.
Хостинг — статический (GitHub Pages), серверов в цепочке нет. Всё, что
страница не может сделать сама (прочитать чужую вкладку), делает букмарклет,
скрипт или расширение руками пользователя — это физический предел браузера,
и он же является границей приватности: выдача передаётся через собственные
вкладки и буфер пользователя.

## Границы (честно)

- Google/Яндекс из дата-центра (IP песочницы/прокси) капчатся — у пользователя
  с домашним IP и своими куками будет настоящая выдача; если поисковик всё же
  показывает капчу — строка статуса честно это покажет: решите её во вкладке и
  нажмите закладку снова;
- «Шаттл» проверен только в Chromium (проба описана выше). В Firefox и Safari
  он должен работать по тем же стандартам (`sessionStorage` наследуется
  окном, открытым с тем же origin, скрипт закрывает окно, открытое скриптом),
  но замеров не было — при неполадках селектор канала переключает на окна;
- вкладка «Шаттла» закрывается сама, потому что открыта скриптом; вкладки,
  открытые вручную по ссылке, браузер может не дать закрыть — на экране релея
  останется подсказка «Ctrl+W»;
- очередь живёт в хранилище самой вкладки: если сайт источника откроет
  выдачу в новой вкладке, копия в ней не появится — страница сообщит о
  потере очереди, источники открываются кнопками;
- вёрстка поисковиков меняется: парсеры в `bridge-lib.js` (букмарклет/скрипт)
  и `core.js` (агрегатор) синхронны по логике; при неполадках payload несёт
  весь HTML — агрегатор разберёт сам;
- параметры диалектов второй волны (регион и язык P6, свежесть P8, дословный
  поиск P11) в адреса источников ещё не встроены: их эффект на живой выдаче
  не измерен. Для каждого в панели есть ссылка «открыть» и отметки
  «сработало / не сработало» — отметки хранятся в localStorage браузера и
  попадают в отчёт этапа 0;
- запрос «бренд + модель» даёт одну карточку на модель: разные модификации
  (диаметр колёс, навеска) оказываются в одном списке источников — точную
  модификацию сверяйте по названию у ссылки.

## Обновление

Сайт публикуется из ветки `main` автоматически: `bash push.sh "что изменилось"`
из корня репозитория → сценарий `checks` → сценарий `publish-web`. Вручную —
вкладка Actions → publish-web → Run workflow. Расширение и скрипт обновляются
из релиза: новый архив вместо старого и «Обновить» на карточке расширения;
скрипт менеджер скриптов берёт сам по адресу `@updateURL`.
